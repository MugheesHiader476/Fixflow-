# ProofOS security model

The trusted identity remains the Clerk subject supplied only by the existing private gateway. Projects inherit `Owned`; no browser tenant, model argument, source document or approval prose grants authority. Customer review requires a separately configured exact authenticated subject and a live request bound to a specific package/version/hash. Owner review and customer acceptance are separate records. Neither Slack discussion nor technical success constitutes contractual acceptance.

All source-derived reads authorize current source/connector selection, ownership and wall-clock lease before decoding. Jobs capture immutable inputs and current source/connector fingerprints; recheck after I/O and before persistence. Disconnect/revocation/selection loss prevents fresh output. Native access is last verified evidence, not instantaneous ACL mirroring. Contract revisions, signed-off requirements, verification executions, packages and approval decisions must not be rewritten by later refreshes. Changes create new versions/executions.

The verification engine consumes strict typed policies and evidence, never LLM verdicts. Wrong repository/SHA/branch/workflow, missing mandatory suite/case coverage, failures, disallowed skips, stale/unavailable evidence and conflicting results fail closed. Technical, delivery, internal review, customer acceptance and invoice eligibility remain distinct. Invoice fields require approved contractual values; no financial action is performed.

Provider HTTP/credentials remain inside native connector modules. Read-only GitHub/Slack/Drive scopes stay read-only. Optional notification/upload controls must be unavailable unless separate grants, destinations, approval, outbox, idempotency, receipts and disclosure checks exist. No arbitrary URLs/shell/tools or live paid-provider retries are introduced.

Packages are private no-store attachments through the authenticated gateway. Customer packages use an explicit allowlist excluding internal discussion and credentials. Approval/downloads recheck authority and exact version; customer decisions use the acting authenticated identity, never a posted approver name. Expired or superseded requests cannot approve another package. Audit records contain identifiers/state transitions, not tokens or full confidential documents.

Existing versioned request/disclosure validation, PostgreSQL budgets, canonical validation, safe errors, path containment and source protections remain mandatory. New agent tools require a material policy-version bump. Existing transcripts are not rewritten to bypass version refusal. Tests use synthetic provider HTTP and a separate PostgreSQL database ending `_test`; live customer actions/deployment are outside this assignment's authorization.
