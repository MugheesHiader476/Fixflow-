The 17 October 2026 request authorizes a small, opt-in stage after FixFlow's parsing reset. The parser still produces **contract 3 / engine 3.0.0** canonical output. Existing parsing jobs, connectors, ownership, history and legacy vectors/chunks remain intact. The implementation was traced through upload registration → durable worker → bounded parser → canonical validation/persistence; native connector envelopes and lifecycle; SQL authorization and canonical reads; PostgreSQL schema/migrations; native structured queries; the Clerk gateway and existing workspace. ## Decisions

| Candidate | Decision and project-specific trade-off |
| --- | --- |
| Structure-aware 450-token target | **Use now.** Pack canonical paragraphs within heading runs; preserve whole functions when they fit the 650-token ceiling. Metadata is included in the budget. Local CPU only. These are starting parameters, not an experimentally optimal size. |
| 650 soft maximum; large chunks | **Use 650 as a hard prompt bound; reject larger output.** Oversized sentences/code can be losslessly split at available boundaries, with a warning for split code. Oversized indivisible table rows fail indexing with review required. Raw/canonical evidence remains stored. |
| Default overlap 0; long prose 40 | **Use now.** Only long prose repeats up to 40 tokens of complete sentences within the same paragraph. Avoid blanket overlap, especially for code, email and tables. This reduces repeated input and indexing work. |
| Metadata prefixes | **Use now.** Project, source, section, date; sender/subject or file/function when available. Missing dates are `Unknown`. Owner-supplied dates are labelled in metadata. Prefix fields are bounded; full provenance stays canonical. Never invent Atlas or a document date for unrelated sources. |
| Emails | **Use now.** Short preferred bodies stay together; long bodies become passages. Store sender, subject, source date, message/thread IDs separately. Original ordered headers and MIME stay canonical/raw. Alternative MIME bodies are not silently added. |
| Slack root + replies, about 600 tokens | **Use query-time composition.** Existing messages have independent source identities and ACL leases. Preserve those rows and citations; fetch authorized root/reply neighbours with the same connection, channel, thread and project. Cap added thread context at 600 tokens. Do not pretend that missing/unselected replies were fetched. |
| Code and tables | **Use now.** Python symbol/AST statement evidence, conservative lexical evidence for other code, exact line spans, header-repeated row ranges, original row numbers/units/cell references where available. No execution or universal language-grammar claim. |
| Lexical versus hybrid retrieval | **Default to PostgreSQL full-text search; use hybrid only explicitly.** Optional Gemini text embeddings and filtered pgvector cosine search add semantic candidates, fused with lexical results using reciprocal ranks. This can address vocabulary mismatch, at the cost of one query API call and source preparation. No extra vector service or framework. Real-world quality and the similarity cutoff require evaluation before changing the default. |
| Neighbour expansion | **Use selectively.** Only a hit near a boundary or explicitly split code triggers expansion; stay in its heading/function or authorized Slack thread. Neighbours count toward six passages and a 3,000-token evidence budget. |
| Deduplication | **Use now.** Suppress repeated IDs, substantially overlapping canonical spans and whitespace/case-equivalent text. Preserve dates, numeric differences, negations and changed statuses. Defer semantic near-duplicate removal: a high similarity score can conceal an important conflicting fact. |
| Caching / changed content | **Use unchanged derived indexes; defer answer-result caching.** Fingerprint source/canonical hashes, chunker revision, project metadata and relevant source metadata. Refresh only opted-in indexes on updates. Request-time SQL access checks remain authoritative. No cross-user or stale answer cache is introduced. |
| Multiple calls / query planning | **Reject for this increment.** No model query expansion, LLM reranking, repair call, automatic retry or agent loop. Synthesis is explicit and uses at most one Responses request, 800 output tokens by default, a 6,000-token local input guard and a 12-second deadline. |
| Exact/latest/current facts | **Use native tools where implemented; defer a general live-fact planner.** Existing connector queries return bounded selected-resource pages/counts with `exact` and `next_cursor`. They do not implement guaranteed latest-email discovery or arbitrary GitHub status tools. Exact/live question patterns abstain with `tool_required`, without search/model calls. Do not infer totals or current status from indexed snapshots. |

The lexical implementation follows [PostgreSQL full-text search controls](https://www.postgresql.org/docs/18/textsearch-controls.html). Token budgets use the fixed [tiktoken `cl100k_base` encoding](https://github.com/openai/tiktoken), not a claimed exact accounting of every possible generator model. The optional adapter follows [Responses structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses); provider-reported usage is returned separately.

## Workflow and operation

1. Apply `myenev/bin/alembic upgrade head` to the intended deployment database after reviewing migrations `0007`–`0009`. No application database is automatically migrated by the evidence APIs.
2. In the existing home workspace, open “Add a parsed source to this project”, refresh the source list, and choose a source and explicit project. One source currently belongs to one search project; adding it again changes that assignment. Optional title/date are owner-supplied labels. Parsing remains the source of content/location evidence.
3. Search with a question and project. `/api/evidence/search` returns evidence only. Both search and answer accept `retrieval: "lexical" | "hybrid"` (default lexical), optional `source_ids` and `expand_context`. `/api/evidence/answer` accepts `synthesize` (default false).
4. For synthesis, configure backend-only `EVIDENCE__API_KEY` and `EVIDENCE__MODEL` with a model supporting strict Responses structured outputs. No model is selected or API key read from a browser. Native settings read `backend/.env`; Docker accepts the same variables from root `.env`. Leave both empty for local search only. No live call is needed to index content.
5. For optional semantic search, set backend-only `GEMINI__API_KEY` and explicitly select `GEMINI__MODEL=gemini-embedding-2`. Click “Prepare semantic search” for an indexed source, then “Refresh semantic status”. A durable background job activates semantic search when the whole source is prepared. Details follow below.
6. `/api/evidence/sources/{id}/remove-index` removes only the derived index and its vectors. Source deletion/purge cascades the new rows. Downgrades refuse while the corresponding derived data exists. There is no bulk backfill or automatic migration of old chunk/vector artifacts.

An index request may set `force: true` to rebuild a damaged or obsolete derived index from the authorized canonical source. Ordinary identical requests reuse the existing fingerprint and passage rows.

SQL filters owner, parsed/active status, project, registered hash, connector state and wall-clock lease **before reading passage payloads**. Canonical reads independently authorize and verify identity/ownership/hash, then reconstruct passage spans. Expansion uses the same checks. Generation rechecks before the outbound call and before returning content. Reassignment, update, deletion or access loss makes prior passage IDs unavailable. No answer cache bypass exists. As with existing connectors, leases reflect last verified access, not instantaneous native ACL mirroring.

The model returns short claims with exact quotes referencing supplied passage IDs. Invented IDs/quotes, refusals, malformed/incomplete responses, timeouts and oversize responses fail safely with no retry. Exact quote validation proves the quotation exists; it does **not** prove semantic entailment, absence of prompt injection effects, or complete factual accuracy. Evaluate synthesis on representative owner-approved data before relying on it. `store=false` disables API response storage for this request; it is not a claim of zero provider retention.

## Optional Gemini embeddings

Semantic search requires **both** `GEMINI__MODEL=gemini-embedding-2` and `GEMINI__API_KEY`. Neither is configured automatically. The supported storage dimension is **768**, selected by `GEMINI__DIMENSIONS=768`; unsupported models/dimensions fail configuration validation. No provider call occurs merely on parsing, startup, indexing, or an ordinary lexical query. API keys stay in the backend. Configure the same values in every API/worker replica. The [Gemini embedding guide](https://ai.google.dev/gemini-api/docs/embeddings) documents supported dimensions; the [REST contract](https://ai.google.dev/api/embeddings) guarantees synchronous batch response order. No SDK dependency is added.

Document instruction: `title: none | text: ...`, with source/project/section/date in the bounded prefix. Query instruction: `task: search result | query: ...`. Model, revision, dimensions and `search-v1` input-format version identify one retrieval space; both documents and queries use this configuration. `GEMINI__REVISION` defaults to the provider's stable model ID. Google does not expose an immutable weights digest here: operators must change this revision label and reprepare sources when rolling out a changed model. Different revision profiles never mix. Migration `0009` preserves earlier vectors as unverified cache entries, without activating or silently reusing them.

`POST /api/evidence/sources/{id}/embed` returns **202** after durably queuing a source; it does no embedding HTTP work. Identical submissions reuse the current job, including its in-flight lease. The application worker processes at most **16 pending passages** per step, independently of the request and across restarts. `GET /api/evidence/sources/{id}/embedding-status` returns `status`, `prepared`, `remaining`, `active`, safe `error`, cumulative embedding attempts and provider-reported input tokens. The UI refreshes status explicitly. `prepared` counts staged cache hits; only `active: true` makes this source eligible for semantic retrieval.

Each passage has a separate request in synchronous `batchEmbedContents`, with `embedContentConfig.outputDimensionality=768` and `autoTruncate=false`. A 24,000-byte per-input guard, 512 KiB response limit and 12-second default deadline (maximum 15) bound calls. No oversized input is silently truncated. The entire positional mapping/count is validated before assigning any vector. Missing, zero-norm, boolean, non-finite and incorrectly sized vectors fail the whole batch; normalization is rechecked before writing. PostgreSQL enforces non-null vectors, dimensions and nonzero norms, and pgvector rejects non-finite elements.

`evidence_embeddings` stores each vector once per source, profile and exact embedding-input hash, with explicit model/revision/dimension/input-format metadata. `passage_embeddings` links those rows to exact passage IDs and the source index fingerprint (canonical hash, source bytes and source/project labels), using composite foreign keys. Passage text and canonical spans remain in the existing passage rows; vector storage adds no text copy. Reuse is confined to the same source and compatible configuration. Changes retain exact unchanged inputs and prune removed inputs. Updates invalidate membership/activation and cancel obsolete jobs; queue preparation again for the new snapshot. This sends only changed inputs. Deletion/index removal/purge cascades memberships, jobs and cache rows. Disconnect, revocation, inactivity and lease expiry immediately exclude rows through the existing SQL access rules; retained cache rows are private and are not proof of authorization.

Completed batches are staged durably. Only when every current passage has a compatible cache entry does one transaction publish all memberships and the source activation pointer. A partial or failed source contributes lexical evidence only. Workers claim expiring leases; no connection or source lock is held over HTTP. Revalidation before sending text and before persistence rejects access, source, project or job changes, with obsolete responses discarded. Durable per-owner rate reservations default to five requests/minute, shared by ingestion and query calls; a source reserves at most one remote batch per 20 seconds. Network failures get at most three consecutive attempts, with persisted exponential delays; malformed output fails without automatic retry. Rate delays are persisted rather than long worker sleeps. Explicit preparation retries a failed job while reusing completed batches. A crash after a billable request but before persistence can repeat that request: database writes are idempotent, provider billing is not guaranteed exactly once. Completed job counters are operational usage evidence, not a billing ledger; crashed/discarded calls and missing provider token reports can remain unknown.

Hybrid queries embed the question at most once and perform **exact filtered cosine search**, followed by Reciprocal Rank Fusion (`k=60`) with the retained PostgreSQL lexical candidates. [pgvector's exact search](https://github.com/pgvector/pgvector#querying) is the initial strategy; no ANN index is added. Owner/project/source, parsed/active state, current source hash/version, connector credentials and wall-clock ACL lease all filter in SQL before payload decoding. Results include passage text, canonical spans, source hashes, lexical/vector ranks, cosine similarity and embedding profile. `candidate_limit` defaults to 24 per retriever (maximum 100); `max_passages` defaults to six (maximum six); `context_tokens` defaults to 3,000 (maximum 3,000). Deduplication and bounded neighbour expansion obey these request limits. Context accounting uses the existing local tokenizer, not a provider billing tokenizer. Missing configuration, incomplete coverage, rate limiting or failed/invalid query embeddings preserve lexical retrieval with visible warnings. `GEMINI__MIN_SIMILARITY=0.5` remains provisional and needs representative model evaluation. Existing exact/live-question abstention and optional synthesis remain unchanged.

No raw multimodal embedding, query cache, cross-owner cache, reranker, query repair, legacy vector backfill or additional vector service is introduced. Approximate indexing requires corpus/latency measurements and a comparison against exact authorized search, including filtered recall. Live Gemini relevance, billing and latency remain unverified when credentials/model are absent. The controlled comparison fixture in `test_vector_jobs.py` reports Recall@3, MRR@3, nDCG@3, p50/p95 ASGI/database latency and document/query embedding usage separately. Its deterministic mock embeddings test ranking/integration; they do not measure Gemini quality or justify a production accuracy claim.
